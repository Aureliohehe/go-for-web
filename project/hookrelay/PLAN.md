# HookRelay 项目总体计划

> 目标：用 6～8 周完成一个基于 Go 和 Asynq 的可靠 Webhook 投递平台，作为可演示、可测试、可解释的后端项目。
> 投入假设：已有 Go 基础，每周约 15～20 小时。只有 4 周时按文末的缩减方案执行。
> 本文描述计划，不代表功能已实现；完成任务并通过验收后再勾选。

## 1. 项目定位

业务系统提交事件，HookRelay 持久化事件，并异步通过 HTTP 投递给指定接收端。接收端故障时自动重试，超过上限后支持人工重放，并保留投递记录。

重点不是接口数量，而是解决以下问题：

1. 数据库写入成功，但任务入队失败，如何避免遗漏？
2. 接收方已经处理成功，但响应丢失，如何处理重复投递？
3. Worker 崩溃、Redis 短暂不可用时，系统如何恢复？
4. 慢接收方如何影响其他任务，如何约束这种影响？
5. 如何通过测试、故障注入和指标证明设计有效？

### 1.1 第一版范围

- 单一调用方，使用开发用 API Key，不实现用户注册与多租户。
- 管理接收端：创建、查询、启用和禁用。
- 每个事件明确指定一个接收端，不实现订阅匹配和一对多分发。
- 幂等接收事件，创建投递记录。
- 异步 HTTP 投递、有限重试、失败重放。
- HMAC 签名及示例接收端的验签与幂等处理。
- 投递历史、结构化日志、基础指标和故障测试。
- Docker Compose 本地部署，不承诺生产级高可用。

### 1.2 暂不做

- 前端控制台、复杂权限、多租户计费。
- DAG 工作流、微服务治理、Kubernetes。
- 自研消息队列、分布式事务框架。
- 任意公网 URL 投递、跨地域容灾。
- 严格事件顺序和业务操作的“恰好一次”保证。

### 1.3 可靠性承诺及边界

- `202 Accepted` 表示事件已经持久化，不表示接收方已经处理成功。
- 正常重试与恢复路径按至少一次投递设计，但有限重试可能最终失败，并不是保证接收方必定收到。
- 稳定的 `delivery_id` 用于接收方幂等；平台单方面不能保证外部副作用恰好发生一次。
- 恢复依赖 MySQL 数据仍然存在，以及服务最终恢复可用；数据库灾难性丢失不在第一版承诺内。
- Asynq 的任务去重不能替代业务幂等，也不能单独解决 MySQL 与 Redis 的一致性。
- 初版只允许投递到显式配置的受控测试地址，不作为任意 URL 的公开转发服务。

## 3. 总体架构

```text
调用方
  │ POST /v1/events
  ▼
API ──同一 MySQL 事务──► events + deliveries + outbox
                                          │
                                     Dispatcher
                                          │ 入队，允许重复
                                          ▼
                                   Redis / Asynq
                                          │
                                        Worker
                                          │ HTTP + HMAC
                                          ▼
                                     模拟接收端
                                          │
Worker ──记录结果──► deliveries + delivery_attempts

Reconciler ──定期检查长期未完成记录，触发受控恢复
```

### 3.1 API

- 校验 API Key、参数、请求体大小和端点状态。
- 通过数据库唯一约束处理并发重复提交，而不只是在插入前查询。
- 创建事件、投递记录和 Outbox 记录的事务成功后才返回接受结果。
- 不在请求 Handler 内发送 Webhook，也不使用无持久化的 `go func()` 代替队列。

### 3.2 Dispatcher

- 扫描可发送的 Outbox 记录，通过短事务领取，使用可过期的处理租约。
- 不持有数据库事务或行锁进行 Redis 网络请求。
- 入队成功后标记已发布；入队失败则记录错误并稍后重试。
- 处理“入队成功、标记失败”的窗口：允许重复入队，任务只携带稳定 ID 和必要的执行版本。
- 第一版先运行一个 Dispatcher；多实例任务领取作为后续增强，不能未经测试就宣称支持。

### 3.3 Worker 与重试

- 使用投递 ID 读取数据库；对已成功记录直接跳过。
- 投递前登记尝试，结束后记录耗时、状态码和脱敏错误。
- Asynq 负责正常执行失败的延迟重试，不再建立一套同时驱动普通重试的数据库调度器。
- MySQL 记录业务状态、实际发送次数及诊断信息；Asynq 重试计数不等于 HTTP 发送次数。
- 重试耗尽、永久性错误或业务过期时将投递置为最终失败。
- 数据库条件更新和执行版本阻止旧任务覆盖新结果；执行租约过期仍可能产生重复 HTTP 请求，接收方必须幂等。
- HTTP 超时应短于任务执行超时；上下文取消传递到 HTTP 请求。

### 3.4 Reconciler 与 Redis 数据丢失

Outbox 已发布并不等于任务已经完成。如果 Redis 丢失已入队数据，仅重试未发布 Outbox 无法恢复这类任务。

- 第一版必须记录这个故障窗口，不能声称 Redis 清空后也天然不丢任务。
- 第六周增加保守的过期检查：查询长期非终态记录，结合任务状态、执行租约和恢复宽限期判断是否需要重新入队。
- 恢复可能重复，因此仍复用稳定投递 ID，并约束恢复频率和总尝试预算。
- 如未完成 Reconciler，只承诺已测试的短暂连接故障恢复，将 Redis 数据丢失后的自动恢复列为已知限制。

## 4. 数据模型

表字段允许随实现调整，修改应通过 SQL migration 留下记录。时间统一使用 UTC。

| 表 | 主要字段 | 约束与用途 |
| --- | --- | --- |
| `endpoints` | id、url、signing_secret、enabled、created_at | 接收端配置；密钥不通过查询接口返回 |
| `events` | id、idempotency_key、request_hash、endpoint_id、event_type、payload、created_at | idempotency_key 唯一，持久化业务事件 |
| `deliveries` | id、event_id、status、generation、attempt_count、last_http_status、last_error、lease_until、created_at、updated_at | 第一版 event_id 唯一；id 是稳定的投递标识 |
| `outbox` | id、delivery_id、generation、status、available_at、lease_until、publish_attempts、last_error | 每轮执行的可靠入队记录，索引支持扫描 |
| `delivery_attempts` | id、delivery_id、generation、started_at、finished_at、http_status、error_class、latency_ms | 追加历史，不因重放而删除 |

实施顺序：第一周先建前三张表；第三周引入 Outbox，投递尝试历史在第四周补齐。

### 4.1 事件接入幂等

- 客户端通过 `Idempotency-Key` 提交幂等键。
- 相同键与相同请求内容返回原有 ID，不重复创建投递。
- 相同键与不同内容返回 `409 Conflict`。
- 第一版明确采用“端点 ID、事件类型及原始 payload 字节”计算请求摘要；JSON 格式变化也可能被判为不同请求，文档须说明。
- 事务内依赖唯一约束裁决竞争，捕获唯一冲突后读取并比较原有事件。
- 第一版不清理幂等记录；未来增加保留期限时，必须说明期限外重复提交的语义。

### 4.2 状态与人工重放

```text
pending → processing → succeeded
               │
               ├─ 可重试错误 → retrying → processing
               └─ 不可重试 / 耗尽预算 → failed

failed ──人工重放──► pending（generation + 1）
```

- 自动重试和人工重放都保持同一个 `delivery_id`，使接收方仍能去重。
- 人工重放只允许最终失败记录，使用条件更新避免并发重放。
- 重放在同一事务内递增 generation、更新状态并写入新 Outbox。
- 任务携带 generation；旧版本任务不应再次执行或覆盖新一轮状态。
- 旧 HTTP 请求可能已在网络中，generation 无法撤回外部副作用。
- 真正要求再次产生业务效果时，应提交一个新事件，而不是重放已有事件。

## 5. HTTP 接口与投递协议

### 5.1 管理 API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/healthz` | 进程存活检查 |
| GET | `/readyz` | 接收请求所需依赖是否就绪 |
| POST | `/v1/endpoints` | 创建受控接收端 |
| GET | `/v1/endpoints/:id` | 查询接收端，不返回密钥 |
| PATCH | `/v1/endpoints/:id` | 启用或禁用端点 |
| POST | `/v1/events` | 幂等接收事件，首次成功返回 202 |
| GET | `/v1/deliveries/:id` | 查询投递状态 |
| GET | `/v1/deliveries/:id/attempts` | 分页查询尝试历史 |
| POST | `/v1/deliveries/:id/replay` | 重放最终失败投递 |

端点禁用后拒绝接收新事件；已有待投递任务在发送前检查并终止为可人工重放的失败。已发出的 HTTP 请求不保证能够撤回。

第一版不允许修改 URL 和签名密钥，避免在途任务配置变化带来的额外语义；变更时创建新端点。

Outbox 完成后，API readiness 主要依赖 MySQL，不应仅因 Redis 短暂断连就拒绝所有事件；同时应对待投递积压设置容量上限，避免无限接收。

### 5.2 Webhook 请求

- 方法：`POST`，内容类型：`application/json`。
- `X-Webhook-ID`：稳定的 delivery_id。
- `X-Webhook-Timestamp`：本次尝试的 Unix 秒时间戳。
- `X-Webhook-Signature`：版本前缀与 HMAC-SHA256 签名。
- 签名输入：`timestamp + "." + delivery_id + "." + 原始请求体字节`。
- 自动重试保持 ID 和消息体稳定，时间戳及签名重新生成。
- 签名必须基于实际发送的原始字节，不能在验签前重新序列化 JSON。

接收端示例验证签名、时间窗口，并使用常量时间比较。以 delivery_id 建立唯一约束，在同一数据库事务中完成去重记录和模拟业务写入。真实外部副作用不一定能放入该事务，需另行设计。

### 5.3 默认错误分类

| 结果 | 处理 |
| --- | --- |
| 2xx | 成功 |
| 网络错误、超时、408、429、5xx | 有限重试 |
| 3xx | 不跟随重定向，按失败处理 |
| 其余多数 4xx | 永久失败 |

退避采用指数增长、随机抖动和最大延迟上限；解析合法 `Retry-After` 时也要设置上限。所有阈值应可配置，并在测试中使用短时间参数。

## 8. 测试与故障矩阵

| 场景 | 预期行为 |
| --- | --- |
| 同一事件并发提交 | 只有一个事件和一个逻辑投递 |
| 相同幂等键、不同内容 | 返回冲突，不覆盖原数据 |
| 事务中途失败 | 事件、投递及 Outbox 一起回滚 |
| Redis 暂时断连 | Outbox 保留，恢复后发布 |
| 入队成功但发布标记失败 | 可能重复执行，但保持相同业务投递 ID |
| Worker 被强制终止 | 任务最终按恢复机制重新处理 |
| 接收端 500 或 429 | 按有限退避策略重试 |
| 接收端处理成功但响应超时 | 允许重投；示例接收端业务效果只有一次 |
| 成功后数据库记录失败 | 允许重投，不宣称平台恰好一次 |
| 签名篡改、时间戳过期 | 接收端拒绝 |
| 并发人工重放 | 只创建一轮新执行 |
| 旧任务晚到 | 不覆盖新 generation 的状态 |
| 单端点长期变慢 | 资源消耗受限，量化其他端点的延迟影响 |
| Redis 已入队数据丢失 | 若完成 Reconciler 则验证恢复，否则列为明确限制 |

单元测试使用 httptest；事务与唯一约束测试必须连接真实 MySQL；队列恢复测试使用真实 Redis。合理使用 `go test -race`，但不把无竞争报告等同于业务正确性证明。

## 9. 压测与观测要求

分别测量“事件接入能力”和“端到端投递能力”，不能用 API 接入 QPS 代替投递吞吐量。

报告至少包含：

- CPU、内存、Go/MySQL/Redis 版本、部署拓扑和配置。
- 并发数、持续时间、载荷大小、端点数量及响应延迟分布。
- 接入吞吐量与错误率。
- 接入到投递成功的 P50/P95/P99 延迟。
- 每秒实际投递次数、成功率、重试率、积压与积压清空耗时。
- CPU、内存、goroutine、数据库连接数和慢查询。
- 重复投递次数与重复业务效果次数，区分两者。
- 优化前后使用同一条件重复测试，保留脚本与原始结果。

不提前编造 QPS 目标，不将单机测试结果描述成生产级容量。指标标签避免使用 event_id、delivery_id 等高基数字段，这些 ID 放入日志。

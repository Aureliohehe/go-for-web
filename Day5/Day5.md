# Day5：Go 工作池与 channel 顺序

## 1. 示例结构

`worker_pool.go` 使用两个管道连接任务生成、计算和结果打印：

```text
主协程生成 Job → jobChan → 工作协程计算 → resultChan → 主协程打印
```

- `Job`：保存任务 ID 和随机数。
- `Result`：保存对应的任务和随机数各位数字的和。
- `jobChan`：传递待处理任务。
- `resultChan`：传递计算结果。
- `createPool`：创建指定数量的工作协程。

## 2. 为什么最初看到的 ID 很大？

原代码的 ID 分配逻辑是：

```go
id := 0
for {
    id++
    // 创建并发送任务
}
```

第一个任务的 ID 实际是 **1**，不是随机数。

但无限循环不断创建任务，结果也不停打印，终端会快速刷屏。看到很大的 ID，可能是前面的输出已经滚走，甚至超过终端的历史保留范围。

另外，输出中的 `randnum` 是 `rand.Int()` 生成的随机数，本身就可能很大，不要将它与 `job id` 混淆。

## 3. 为什么多个工作协程会导致乱序？

```go
createPool(64, jobChan, resultChan)
```

这会启动 64 个工作协程，共同从 `jobChan` 接收任务。

channel 是先进先出（FIFO）的队列，但它只能保证队列中数据的顺序，不能保证多个工作协程的完成顺序。

例如：

```text
工作协程 A：取到任务 1 → 暂时被调度器挂起 → 稍后发送结果
工作协程 B：取到任务 2 → 完成计算 → 先发送结果

打印顺序：2、1
```

即使每个任务的计算很简单，协程调度也可能导致乱序。

**任务发送顺序、任务完成顺序、结果发送顺序不是同一个概念。**

只有一个协程负责打印，也不能使乱序到达的结果自动恢复为 ID 顺序。

## 4. 当前代码为什么按 ID 顺序打印？

当前代码只创建 10 个任务，并使用 1 个工作协程：

```go
createPool(1, jobChan, resultChan)

const jobCount = 10
for id := 1; id <= jobCount; id++ {
    jobChan <- &Job{
        Id:      id,
        RandNum: rand.Int(),
    }
}
close(jobChan)

for i := 0; i < jobCount; i++ {
    result := <-resultChan
    fmt.Printf("job id:%v randnum:%v result:%d\n",
        result.job.Id, result.job.RandNum, result.sum)
}
```

顺序成立的原因：

1. 主协程按 `1～10` 的顺序发送任务。
2. 唯一的工作协程按顺序取出任务。
3. 工作协程计算并发送当前结果后，才处理下一个任务。
4. 主协程按结果进入 `resultChan` 的顺序接收并打印。

```text
顺序发送 → 单协程顺序处理 → 顺序接收并打印
```

因此，ID 会按照 `1、2、3……10` 打印。

## 5. 为什么在主协程中接收结果？

`main` 函数返回时，程序会退出，不会自动等待其他协程结束。

当前主协程明确接收 10 个结果，能确保全部任务结果打印完毕后再退出，不需要用 `time.Sleep` 猜测等待时间。

## 6. 关闭 channel 的作用

```go
close(jobChan)
```

表示不会再发送新任务。工作协程仍可接收管道中已经发送的任务；管道关闭且数据全部取完后：

```go
for job := range jobChan {
    // 处理任务
}
```

这个循环就会结束。

注意：

- 通常由发送方在确认不再发送时关闭管道。
- 向已关闭的管道发送数据会 panic。
- 重复关闭管道会 panic。
- 关闭管道不等于丢弃其中尚未接收的数据。
- 当前按已知数量接收结果，不需要关闭 `resultChan` 才能结束循环。
- 如果改为 `for result := range resultChan`，则需要在所有工作协程发送完毕后关闭 `resultChan`，通常用 `sync.WaitGroup` 协调。

## 7. 当前写法的缓冲区限制

当前两个管道的缓冲容量都是 128，而任务只有 10 个，因此可以先发送全部任务，再接收结果。

如果将任务数量大幅增加，仍采用“先全部发送，再接收结果”的方式，就可能死锁：

```text
resultChan 满 → 工作协程阻塞，无法继续取任务
jobChan 满 → 主协程阻塞，无法进入接收结果阶段
```

处理大量任务时，应让任务发送与结果接收并发进行，例如单独开启一个生产者协程发送任务，并由主协程持续接收结果。

## 8. 多工作协程也能按 ID 打印吗？

可以，但需要额外排序或重排：

- **有限批次**：收集全部结果，按任务 ID 排序后打印。
- **持续处理**：缓存提前到达的结果，记录下一个应打印的 ID，等对应结果到达后按顺序打印。

总结：**单工作协程天然保持本例的处理顺序；多工作协程不保证结果顺序，需要额外协调。**

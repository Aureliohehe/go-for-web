# Day5：Go 并发——工作池、select 与同步锁

## 1. 示例结构

本节通过以下示例学习任务分发、channel 多路选择以及共享数据的同步：

| 文件 | 学习内容 | 当前状态 |
| --- | --- | --- |
| `worker_pool.go` | 工作池、channel、结果顺序 | 全部代码已注释 |
| `select.go` | 使用 `select` 等待多个 channel | 可单独运行 |
| `sync/mutex.go` | `sync.Mutex` 保护共享计数器 | 全部代码已注释 |
| `sync/RwMutex.go` | `sync.RWMutex` 区分读写操作 | 可单独运行 |

以下工作池和互斥锁的说明针对文件中保留的示例逻辑；运行前需要取消注释。

`worker_pool.go` 使用两个管道连接任务生成、计算和结果打印：

```text
主协程生成 Job → jobChan → 工作协程计算 → resultChan → 主协程打印
```

- `Job`：保存任务 ID 和随机数。
- `Result`：保存对应的任务和随机数各位数字的和。
- `jobChan`：传递待处理任务。
- `resultChan`：传递计算结果。
- `createPool`：创建指定数量的工作协程。

## 2. 为什么最初看到的 ID 很大？

原代码的 ID 分配逻辑是：

```go
id := 0
for {
    id++
    // 创建并发送任务
}
```

第一个任务的 ID 实际是 **1**，不是随机数。

但无限循环不断创建任务，结果也不停打印，终端会快速刷屏。看到很大的 ID，可能是前面的输出已经滚走，甚至超过终端的历史保留范围。

另外，输出中的 `randnum` 是 `rand.Int()` 生成的随机数，本身就可能很大，不要将它与 `job id` 混淆。

## 3. 为什么多个工作协程会导致乱序？

```go
createPool(64, jobChan, resultChan)
```

这会启动 64 个工作协程，共同从 `jobChan` 接收任务。文件中“使用 1 个工作协程”的注释与参数不一致，应以实际传入的 `64` 为准；若要使用单个工作协程，需要改为 `createPool(1, jobChan, resultChan)`。

channel 是先进先出（FIFO）的队列，但它只能保证队列中数据的顺序，不能保证多个工作协程的完成顺序。

例如：

```text
工作协程 A：取到任务 1 → 暂时被调度器挂起 → 稍后发送结果
工作协程 B：取到任务 2 → 完成计算 → 先发送结果

打印顺序：2、1
```

即使每个任务的计算很简单，协程调度也可能导致乱序。

**任务发送顺序、任务完成顺序、结果发送顺序不是同一个概念。**

只有一个协程负责打印，也不能使乱序到达的结果自动恢复为 ID 顺序。

## 4. 为什么在主协程中接收结果？

`main` 函数返回时，程序会退出，不会自动等待其他协程结束。

工作池示例中，主协程明确接收 10 个结果。在每个任务都成功发送一个结果的前提下，这能确保全部任务结果打印完毕后再退出，不需要用 `time.Sleep` 猜测等待时间。

不过，收齐结果不等于所有工作协程都已经返回；若需要明确等待协程退出，可以使用后文的 `sync.WaitGroup`。

## 5. 关闭 channel 的作用

```go
close(jobChan)
```

表示不会再发送新任务。工作协程仍可接收管道中已经发送的任务；管道关闭且数据全部取完后：

```go
for job := range jobChan {
    // 处理任务
}
```

这个循环就会结束。

注意：

- 通常由发送方在确认不再发送时关闭管道。
- 向已关闭的管道发送数据会 panic。
- 重复关闭管道会 panic。
- 关闭管道不等于丢弃其中尚未接收的数据。
- 当前按已知数量接收结果，不需要关闭 `resultChan` 才能结束循环。
- 如果改为 `for result := range resultChan`，则需要在所有工作协程发送完毕后关闭 `resultChan`，通常用 `sync.WaitGroup` 协调。

## 6. 工作池写法的缓冲区限制

当前两个管道的缓冲容量都是 128，而任务只有 10 个，因此可以先发送全部任务，再接收结果。

如果将任务数量大幅增加，仍采用“先全部发送，再接收结果”的方式，就可能死锁：

```text
resultChan 满 → 工作协程阻塞，无法继续取任务
jobChan 满 → 主协程阻塞，无法进入接收结果阶段
```

处理大量任务时，应让任务发送与结果接收并发进行，例如单独开启一个生产者协程发送任务，并由主协程持续接收结果。

## 7. 多工作协程也能按 ID 打印吗？

可以，但需要额外排序或重排：

- **有限批次**：收集全部结果，按任务 ID 排序后打印。
- **持续处理**：缓存提前到达的结果，记录下一个应打印的 ID，等对应结果到达后按顺序打印。

总结：**单工作协程天然保持本例的处理顺序；多工作协程不保证结果顺序，需要额外协调。**

## 8. select：同时等待多个 channel

`select.go` 创建两个无缓冲 channel，并启动两个协程：

```go
output1 := make(chan string)
output2 := make(chan string)
go test1(output1) // 等待 5 秒后发送 "test1"
go test2(output2) // 等待 2 秒后发送 "test2"

select {
case s1 := <-output1:
    fmt.Println("s1=", s1)
case s2 := <-output2:
    fmt.Println("s2=", s2)
}
```

### 8.1 为什么通常只打印 test2？

通常约 2 秒后，`test2` 先准备好发送数据，`select` 执行第二个分支：

```text
s2= test2
```

这里有三个关键点：

1. 无缓冲 channel 的发送需要与接收配对，不是写入后就立即返回。
2. **一次 `select` 只选择并执行一个分支**，不会自动等待其他分支，也不会自动循环。
3. 分支执行完毕后，`main` 返回，程序退出，因此不会继续等到第 5 秒打印 `test1`。

`select` 不会取消未选中的协程。本例是整个程序退出了；如果主协程继续运行却不再接收 `output1`，`test1` 就可能一直阻塞在发送操作上。

### 8.2 select 的选择规则

- 只有一个通信分支就绪：执行该分支。
- 多个通信分支同时就绪：伪随机选择一个，不按代码书写顺序确定优先级。
- 没有分支就绪且没有 `default`：阻塞等待。
- 没有分支就绪但有 `default`：立即执行 `default`。
- 对 `nil` channel 的通信永远不会就绪，可以用它禁用某个分支。
- 已关闭的 channel 在数据取完后，接收仍会立即返回零值；可用 `value, ok := <-ch` 判断是否已关闭且取空。

因此，“先打印 test2”是本例正常调度下的预期现象，并不是 `select` 为第二个分支设置了优先级。

### 8.3 如果两个结果都要接收怎么办？

本例已知每个 channel 只发送一次，可以把原来的 `select` 替换为：

```go
for i := 0; i < 2; i++ {
    select {
    case s1 := <-output1:
        fmt.Println("s1=", s1)
    case s2 := <-output2:
        fmt.Println("s2=", s2)
    }
}
```

这样主协程会接收两次，通常先收到 `test2`，再收到 `test1`。这个写法依赖“总共发送两条消息”的约定，不适用于数量未知的数据流。

处理会关闭的 channel 时，应检查 `ok`，并将已关闭且取空的 channel 变量设为 `nil`，避免循环反复选中关闭的 channel。

### 8.4 default 与超时的区别

```go
select {
case msg := <-output1:
    fmt.Println(msg)
case <-time.After(3 * time.Second):
    fmt.Println("等待超时")
}
```

这是等待数据或超时；`default` 则是不等待，不能替代超时机制。

注意：超时只让接收方停止等待，并不会自动停止发送方。实际程序中，可通过 `context` 或退出信号让发送方也能结束，避免协程一直阻塞。不要为“通知取消”而直接关闭仍有协程可能发送的 channel，否则发送方会 panic。

另外，在 `for` 循环中使用空的 `default` 可能造成忙等，持续占用 CPU。

## 9. sync.Mutex：保护共享变量

`sync/mutex.go` 中，两个协程各自执行 5000 次 `x = x + 1`，并用互斥锁保护每次更新：

```go
func add() {
    for i := 0; i < 5000; i++ {
        lock.Lock()
        x = x + 1
        lock.Unlock()
    }
    wg.Done()
}
```

### 9.1 为什么加一也需要加锁？

`x = x + 1` 是“读取旧值 → 计算 → 写回”的读改写操作，不是一个有并发安全保证的原子操作。

例如，两个协程都读到 `x == 10`，然后都写回 `11`，就会丢失一次更新。不加锁会产生数据竞争，即使某次恰好输出 `10000`，也不能说明代码正确。

`Lock()` 到 `Unlock()` 之间是**临界区**。同一时刻，只有一个协程能持有这把互斥锁；其他尝试获取它的协程需要等待。

本例中，所有更新都使用同一把锁，并在主协程等待两个协程结束后读取 `x`，因此最终结果为：

```text
10000
```

### 9.2 使用锁的注意事项

- 对同一份共享数据的并发访问，需要遵守同一套同步规则，不能只锁部分写操作而让其他访问绕过锁。
- `sync.Mutex` 的零值可直接使用，不需要额外初始化。
- 锁使用后不要复制；在结构体或函数之间传递时，通常使用指针。
- 锁不可重入：持锁期间再次获取同一把锁，会阻塞自己。
- `Unlock()` 必须与加锁操作匹配；遗漏解锁会让等待者无法继续。
- 临界区应尽量小，不要在持锁期间执行不必要的耗时操作。

普通函数中常用 `defer lock.Unlock()` 保证返回时解锁。但不要直接在这里的循环体中每次加锁后都 `defer` 解锁：`defer` 要等整个函数返回才执行，下一轮再次加锁就会阻塞。

## 10. sync.WaitGroup：等待一组协程完成

两个锁示例都使用了 `sync.WaitGroup`：

```go
wg.Add(2)
go add()
go add()
wg.Wait()
fmt.Println(x)
```

- `Add(n)`：增加待完成任务的计数。
- `Done()`：完成一个任务，计数减一。
- `Wait()`：阻塞到计数归零。

应在启动对应协程之前调用 `Add`，避免 `Wait` 在任务尚未登记时就返回。任务函数中通常可以写成：

```go
func add() {
    defer wg.Done()
    // 执行任务
}
```

这是对原函数中末尾 `wg.Done()` 的替代，不要保留两次调用，否则可能使计数变成负数并触发 panic。

**WaitGroup 解决“何时完成”，Mutex 解决“共享数据如何安全访问”**，两者不能互相替代。只调用 `Wait()`，不能防止两个工作协程同时修改 `x`。

在工作池中，也可以登记所有工作协程，让每个协程退出时调用 `Done()`，再由一个协调协程等待并关闭结果管道：

```go
// 前提：所有工作协程已登记，且退出时都会调用 Done。
go func() {
    wg.Wait()
    close(resultChan)
}()

for result := range resultChan {
    fmt.Println(result)
}
```

不要让某个工作协程单独关闭 `resultChan`，因为其他协程可能还需要发送结果。也不要在主协程中先 `Wait()` 再接收结果，否则工作协程可能因结果管道写满而无法完成。

## 11. sync.RWMutex：区分读锁和写锁

`sync/RwMutex.go` 启动了 10 个写协程和 1000 个读协程：

- 写操作：`rwlock.Lock()` / `rwlock.Unlock()`，持锁期间模拟耗时 10 毫秒。
- 读操作：`rwlock.RLock()` / `rwlock.RUnlock()`，持锁期间模拟耗时 1 毫秒。
- 主协程：使用 `wg.Wait()` 等待全部完成，再打印总耗时。

注意：`write()` 中“假设读操作耗时 10 毫秒”的注释应理解为“假设写操作耗时 10 毫秒”；当前 `read()` 只模拟耗时，没有实际读取 `x`。若加入读取，应放在读锁保护范围内。

### 11.1 读写锁的互斥关系

| 操作组合 | 能否同时持锁 |
| --- | --- |
| 读与读 | 可以 |
| 读与写 | 不可以 |
| 写与写 | 不可以 |

读锁允许多个读协程一起访问数据，但**不能在持有读锁时修改共享数据**。写锁是独占的，既排斥其他写者，也排斥读者。

当写者正在等待锁时，新的读锁请求也会受到阻塞，避免不断到来的读者让写者一直无法获得锁。因此不能把“读读可并发”理解为“读锁永远不会等待”。

`RWMutex` 不支持直接把读锁升级为写锁，也不支持直接把写锁降级为读锁；如果先释放再重新获取锁，中间的数据可能已经被其他协程修改。

### 11.2 为什么这个例子中读写锁通常更快？

如果所有读写操作都使用同一把 `Mutex`，持锁区间只能串行执行，仅模拟等待时间相加就约为：

```text
10 × 10ms + 1000 × 1ms = 1100ms
```

使用 `RWMutex` 后，写操作仍互斥，但多个读操作的等待时间可以重叠，所以这个读多写少、读操作耗时明显的示例通常会更快。

实际耗时还受到协程调度、计时器精度、机器负载等影响，不能保证固定数值。`RWMutex` 也不是总比 `Mutex` 快：读操作很短或写操作频繁时，其管理开销可能抵消收益，应以实际基准测试为准。

### 11.3 如何对比两种锁？

当前代码启用的是 `rwlock`，`lock` 的操作被注释。要测试互斥锁版本，需要在 `read()` 和 `write()` 中**一起**切换：

- 注释全部 `rwlock` 的加锁、解锁操作。
- 启用全部 `lock.Lock()` 和 `lock.Unlock()`。
- 保持协程数量和模拟耗时一致，多次运行观察。

不能让读者使用 `lock`、写者使用 `rwlock`：它们是两把独立的锁，无法为同一份数据提供互斥保护。

在 `Day5` 目录下，显式指定文件运行当前启用的示例：

```bash

```

取消对应文件的注释后，可以单独运行：

```bash

```

这些示例各自定义了 `main`，部分还定义了同名全局变量，因此应按文件运行，不要在全部启用后直接一起编译。当前全注释文件连 `package` 声明也被注释，按目录编译还可能遇到语法错误。

运行前需确保本地 Go 工具链能够满足仓库 `go.mod` 的版本要求。竞态检测器只检查本次实际执行到的路径，未报告问题不等于绝对没有并发问题。

| 工具 | 主要用途 | 不负责什么 |
| --- | --- | --- |
| channel | 协程间传递数据、同步通信 | 不自动保证多个工作协程按任务 ID 完成 |
| select | 从多个可执行的 channel 操作中选择一个 | 不自动循环、等待所有结果或取消其他协程 |
| Mutex | 互斥访问共享数据 | 不等待一组任务结束 |
| RWMutex | 允许并发读、保证独占写 | 不允许读锁内修改共享数据 |
| WaitGroup | 等待一组任务完成 | 不保护任务之间的共享数据访问 |

核心思路：**用 channel 传递任务与结果，用 select 协调多个通信操作，用锁保护共享数据，用 WaitGroup 等待任务结束。**
